# グローバル指示

## 言語・説明ルール

- ツール呼び出しの前に、何をするか・なぜするかを日本語で簡潔に説明すること

## 環境設定の変更ルール

- 環境設定やdotfilesなど影響範囲が見えにくい変更は、全体像を示したうえで原子的な単位に分け、1件ずつ内容を説明して了承を得てから実行する

## 外部ツール連携ルール

### GitHub

- GitHub 操作では `github-cli` skill を使うこと
- GitHub 操作は必ず `gh` CLI を使うこと
- GitHub MCP server は使用しないこと

## 文章執筆ルール

- 日本語で記事・解説文・ドキュメントなどの読み物を書く、または推敲・リライトするときは、`cognitive-rhythm-writing` skillと、その依存先の`japanese-tech-writing` skillを使うこと

## コーディング原則

- コードの実装・修正・レビュー・リファクタリングを行うときは、`karpathy-guidelines` skillを使うこと

## Superpowers運用ルール

### brainstormingの適用範囲

- 次に該当する場合は`brainstorming`をスキップしてよい
  - 明らかに単純なタスク（コミット、push、1ファイルの軽微な修正など）
  - コード変更を伴わない作業（調査、説明、レビュー、質問への回答）
  - ユーザーが手順や変更内容を具体的に指定して依頼したもの

### subagent-driven-developmentの適用範囲

- 手順の重さは修正の規模に合わせる。数ファイルの機械的な変更（リネーム、コメント削除、指定どおりの一括置換）にSDDを使わない。ブリーフ執筆、サブエージェント派遣、レビューパッケージ生成、レビュー読解の固定費が、直接編集して検証するより高くつくため
- SDDを使うのは、複数タスクにまたがる計画の実行、設計判断を伴う実装、レビューのゲートを挟む価値がある変更とする
- 判断に迷ったら「レビュアーが片方を却下しつつ他方を承認しうるか」を基準にする。答えがNoならSDDは不要
